# 알고리즘 문서 형식 규칙

`requirement_docs/algorithm/` 의 기존 문서(`pw_cp_constructor_run.md`,
`initialize_by_tau_coarsened_cp.md`)와 일관된 문서를 만들기 위한 형식 규칙이다.
새 문서는 이 둘 옆에 두었을 때 이질감이 없어야 한다.

## 고정 골격

모든 문서는 아래 순서를 따른다. 가운데의 "알고리즘별 상세 섹션"만 대상에 맞게
달라지고, 나머지는 고정이다.

```md
# <알고리즘 이름> (<영문 슬러그/약어>)

호출: `def <함수명>` (<파일명>.py)

## 개요
## 문제 설명
### 파라미터 (Parameters)
### 변수 (Variables)
### 목적 (Objective)
### 제약 (Constraints)
## 핵심 아이디어
## <알고리즘별 상세 섹션들>          ← 대상마다 다름. 섹션 골격 단계에서 합의
## 전체 실행 흐름
## 파라미터 요약
## 주의사항 및 응용 고려사항
```

`개요 → 문제 설명 → 핵심 아이디어` 순서가 이 골격의 핵심이다. 독자가 5요소를
스스로 분류하는 인지 부담을 지지 않도록, **「문제 설명」이
parameter·variable·objective·constraint 를 이 순서대로 라벨링해 보여주고,
「핵심 아이디어」가 mechanism을 설명한다.** 알고리즘별 상세 섹션은 그 뒤에서
mechanism을 더 깊이 풀어 쓴다.

- **제목**: 한국어 이름 + 괄호 안에 코드에서 쓰는 영문 약어/슬러그.
  예: `# PW-CP (Prefix-Window CP) 알고리즘`.
- **호출 줄**: 제목 바로 아래 한 줄. `호출: \`def 함수명\` (파일명.py)` 형식.
  메서드면 정의된 파일명을 쓴다.
- 섹션은 `---` 수평선으로 시각적으로 구분해도 좋다(기존 문서가 그렇게 한다).

## 각 고정 섹션의 내용

- **개요**: 3~6문장. 알고리즘이 무엇이고 어떤 전략을 쓰는지, 어떤 입력에서
  출발해 무엇을 산출하는지. 적용 조건(문제 종류, 목표)을 짧게 덧붙인다.
- **문제 설명**: 알고리즘을 하나의 최적화/탐색 문제로 규정하는 섹션.
  `### 파라미터` → `### 변수` → `### 목적` → `### 제약` 4개 하위 섹션을 이
  순서대로 둔다. 독자가 각 요소가 무엇인지 짐작할 필요가 없도록 라벨이 곧
  답이 된다.
  - `### 파라미터`: 알고리즘을 제어하는 입력 설정값을 부류별로 묶어 개념
    설명한다(예: "시간 예산 계열", "탐색 강도 계열"). 전체 목록과 기본값은
    중복 서술하지 말고 뒤쪽 「파라미터 요약」 표를 한 줄로 가리킨다.
  - `### 변수`: 알고리즘이 풀이 과정에서 결정·추적하는 변수/상태. CP면
    결정변수와 도메인, 휴리스틱이면 incumbent·후보 집합 등 추적 상태.
  - `### 목적`: 무엇을 최소화/최대화하는가. 직접 목적함수와 최종 목표의
    연결. 분기로 목적이 바뀌면 각 경우를 명시.
  - `### 제약`: 해가 지켜야 할 제약. CP면 제약식, 휴리스틱이면 절차가
    보장하는 불변식으로 서술. 휴리스틱이라 명시적 제약 객체가 없어도 이
    하위 섹션을 생략하지 않는다.
- **핵심 아이디어**: 이 섹션이 곧 mechanism이다. 번호 매긴 목록으로 핵심
  통찰 3~5개. 문제 설명의 4요소(파라미터·변수·목적·제약)를 어떻게 엮어 해를
  만들고 개선하는지, "왜 이렇게 하는가"라는 설계 의도가 드러나야 한다.
  단순 절차 나열이 아니다.
- **전체 실행 흐름**: ```text``` 블록 안에 입력 → 단계별 의사코드/순서도. 분기와
  반복을 들여쓰기로 표현한다. 코드의 제어 흐름과 일치해야 한다.
- **파라미터 요약**: 마크다운 표. 컬럼은 `파라미터 | 기본값 | 설명` 또는
  `파라미터 | 타입 | 설명`. 파라미터가 많으면 범주별로 표를 나눈다(기존
  tau-coarsened 문서가 그렇게 한다). 이름·기본값·타입은 코드에서 검증한 값.
- **주의사항 및 응용 고려사항**: 문서가 코드에 과적합되지 않게 하는 섹션. 다음을
  포함한다 — 필수 전제(예: 초기 실행 가능해 필요), 다른 문제에 적용할 때 바꿔야
  할 부분(확장 포인트), 잘못 쓰면 생기는 함정. 기존 문서의 "다른 문제에 응용할
  때 고려사항" / "주의사항 및 설계 고려사항" 섹션을 본보기로 삼는다.

## 표현 도구

- **마크다운 표**: 영역 분류, 파라미터, 분기별 동작 비교 등 정형 정보에 사용.
- **```text``` ASCII 다이어그램**: 타임라인, 윈도우 구조, 파이프라인 순서도,
  의사코드에 사용. 기존 문서의 타임라인 그림·순서도를 참고.
- **인라인 코드**: 변수명·함수명·파라미터명은 항상 백틱으로 감싼다.
- 수식이 필요하면 ```text``` 블록 안에 평문으로 쓴다(LaTeX 쓰지 않음).

## 톤

- 한국어 명세서 톤. "~한다", "~이다" 체. 평서·단정형.
- 정확하되 장황하지 않게. 각 섹션은 필요한 만큼만.
- 코드를 그대로 베끼지 말고 의도를 설명한다. 단, 함수·파라미터명은 정확히.
- 길이는 대상 복잡도에 비례한다. 기존 문서는 120~380줄 범위다. 단순한
  알고리즘을 억지로 늘리지 말 것.

## 분량 가이드

- 단순한 constructor/휴리스틱: 80~150줄
- 다단계 파이프라인/복잡한 CP 서브루틴: 200줄 이상도 무방

핵심은 줄 수가 아니라, 읽는 사람이 코드를 열지 않고도 알고리즘을 재현·응용할 수
있을 만큼의 정보가 정확하게 담겼는가이다.
