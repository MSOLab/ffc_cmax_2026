# Algorithm Doc Writer

hybridflowshop 코드베이스에 **이미 구현된** 알고리즘을 한국어 명세 문서로 만들어
`requirement_docs/algorithm/` 에 저장하는 스킬이다.

이 문서들의 목적은 두 가지다: (1) 미래의 개발자(주로 사용자 본인)가 알고리즘의
동작을 코드를 다시 읽지 않고도 이해하게 하는 것, (2) 같은 아이디어를 다른 문제에
응용할 수 있도록 일반화된 설계 지식을 남기는 것. 따라서 문서는 코드의 단순
재서술이 아니라, **정확하면서도 설계 의도가 드러나는** 명세여야 한다.

## 가장 중요한 원칙: 코드 그라운딩

이 문서의 가치는 전적으로 **정확성**에서 나온다. 파라미터 이름, 기본값, 실행
순서, 호출되는 헬퍼 함수를 절대 추측하지 말 것. 모르면 코드를 읽어서 확인한다.
틀린 파라미터명 하나가 문서 전체의 신뢰를 무너뜨린다.

문서를 쓰기 전에 반드시:

- 대상 함수/메서드의 **본문 전체**를 읽는다.
- 본문이 호출하는 주요 헬퍼(`_build_...`, `_solve_...` 등)도 따라가서 읽는다.
- 파라미터의 **이름·타입·기본값**은 함수 시그니처 또는 관련 dataclass/설정
  클래스에서 직접 확인한다. `cpsat_model_2/params.py`, `hfs_config.py`,
  컨트롤러 메서드 시그니처 등이 출처가 된다.
- 실행 순서는 코드의 제어 흐름을 그대로 따른다. 분기(if/else)가 있으면 문서에도
  분기로 표현한다.

## 문서 구조: 5요소를 그대로 드러낸다

알고리즘을 이해·재현하려면 parameter / variable / objective / constraint /
mechanism 5가지가 핵심이다. 독자가 문서를 읽으며 "이건 변수겠지, 이건
목적함수겠지" 하고 스스로 분류하는 인지 부담을 지지 않도록, **문서 구조
자체가 이 5요소를 순서대로 명시적으로 드러내야 한다.**

- **개요** 다음에 곧바로 **「문제 설명」** 섹션을 두고, 그 안에서
  parameter → variable → objective → constraint 를 **이 순서대로** 각각
  별도 하위 섹션(`### 파라미터`, `### 변수`, `### 목적`, `### 제약`)으로
  명시한다.
- 이어지는 **「핵심 아이디어」** 섹션이 곧 mechanism — 위 4요소를 엮어
  해를 만들고 개선하는 핵심 절차 — 의 설명이다.

| 요소 | 문서 위치 | 담아야 할 것 |
|------|-----------|--------------|
| **Parameter** | 문제 설명 › 파라미터 | 알고리즘 동작을 제어하는 입력 설정값을 부류별로 개념 설명. 전체 목록·기본값은 뒤쪽 「파라미터 요약」 표를 가리킨다. |
| **Variable** | 문제 설명 › 변수 | 알고리즘이 풀이 과정에서 다루는 결정/상태 변수. CP 모델이면 결정변수와 도메인, 휴리스틱이면 추적 상태(incumbent, 후보 집합 등). |
| **Objective** | 문제 설명 › 목적 | 무엇을 최소화/최대화하는가. 직접 목적함수와 최종 목표(예: makespan)의 연결. 분기로 목적이 바뀌면 각 경우 명시. |
| **Constraint** | 문제 설명 › 제약 | 해가 반드시 지켜야 하는 제약. CP 모델이면 제약식 형태로, 휴리스틱이면 절차가 보장하는 불변식으로. |
| **Mechanism** | 핵심 아이디어 | 위 요소들을 엮어 해를 만들고 개선하는 핵심 절차. 알고리즘별 상세 섹션이 이를 더 풀어 쓴다. |

대상이 CP 기반이면 variable/objective/constraint 가 CP 모델로 명확히
드러나고, 순수 휴리스틱이면 절차 속 암묵적 형태로 존재한다 — 어느 쪽이든
「문제 설명」에서 이를 명시적으로 끄집어내 라벨을 붙여 설명한다. 휴리스틱이라
"변수"나 "제약"이 코드에 명시적 객체로 없더라도 하위 섹션을 생략하지 말고,
절차가 다루는 상태·불변식을 변수·제약으로 서술한다.

## 작업 흐름

### 1. 대상 식별

사용자는 함수명(`critical_cone_cp`) 또는 파일 경로(`neh_cp.py`)로 대상을
지정한다. 모호하면 `grep` 으로 정의 위치를 확정한다. 대상이 여러 곳에 있거나
어느 것인지 불분명하면 사용자에게 되묻는다.

### 2. 코드 정독

위 "코드 그라운딩" 원칙대로 대상 코드와 헬퍼, 파라미터 출처를 모두 읽는다.
이미 문서화된 알고리즘(`requirement_docs/algorithm/` 의 기존 `.md`)을 호출하거나
재사용하는 부분이 있으면, 그 문서를 중복 서술하지 말고 한 줄로 참조만 한다.

### 3. 섹션 골격 제안 → 승인 (생략하지 말 것)

문서를 바로 쓰지 말고, 먼저 **이 알고리즘에 맞는 섹션 구성**을 사용자에게
제안한다. 고정 섹션(개요 → 문제 설명 → 핵심 아이디어 → … → 전체 실행 흐름
→ 파라미터 요약 → 주의사항)은 그대로 두고, 그 사이에 들어갈 **알고리즘별
상세 섹션**을 어떻게 나눌지를 제목 리스트로 보여준다. 예:

```
제안하는 섹션 구성 (critical_cone_cp):
  ## 개요
  ## 문제 설명
    ### 파라미터   ### 변수   ### 목적   ### 제약
  ## 핵심 아이디어                ← mechanism
  ## Critical Cone 선정           ← 알고리즘별
  ## 연산 집합 트리밍             ← 알고리즘별
  ## CP 서브문제 구성             ← 알고리즘별
  ## 적용 및 수락 기준            ← 알고리즘별
  ## 전체 실행 흐름
  ## 파라미터 요약
  ## 주의사항 및 응용 고려사항
```

사용자가 승인하거나 수정하면 그 구성대로 작성한다. 이 단계는 대상이 복잡할 때
헛수고를 막아주므로 건너뛰지 않는다.

### 4. 문서 작성

승인된 골격대로 `references/format.md` 의 형식 규칙을 따라 작성한다.

### 5. 저장

`requirement_docs/algorithm/<함수명>.md` 로 저장한다. 파일명은 대상
함수/메서드명을 그대로 쓴다(snake_case, `.md`). 예: `critical_cone_cp` →
`critical_cone_cp.md`. `.html` 은 만들지 않는다.

## 문서 형식

문서는 한국어로, 명세서/교육용 톤으로 작성한다. 정확한 형식 규칙(고정 섹션
골격, 표·다이어그램 작성법, 톤)은 `references/format.md` 에 있으니 작성 직전에
읽는다.

가장 좋은 참고 자료는 **이미 존재하는 문서**다. 작성 전
`requirement_docs/algorithm/pw_cp_constructor_run.md` 와
`initialize_by_tau_coarsened_cp.md` 를 읽고 그 구조·밀도·톤을 본보기로 삼는다.
새 문서가 그 옆에 자연스럽게 놓이도록 일관성을 맞춘다.

## 품질 체크리스트

문서를 저장하기 전에 스스로 점검한다:

- [ ] 「문제 설명」에 파라미터·변수·목적·제약 4개 하위 섹션이 이 순서대로
      있고, 「핵심 아이디어」가 mechanism을 설명하는가?
- [ ] 모든 파라미터명·기본값이 실제 코드와 일치하는가? (시그니처/dataclass 대조)
- [ ] 실행 흐름의 분기가 코드의 if/else 와 일치하는가?
- [ ] `호출:` 줄에 정확한 함수명과 파일명이 적혀 있는가?
- [ ] "주의사항 및 응용 고려사항" 섹션이 있어 코드 과적합을 피했는가?
- [ ] 기존 두 문서와 톤·구조가 일관되는가?
- [ ] 추측하거나 확신 없이 쓴 문장이 없는가? (있으면 코드를 다시 확인)
